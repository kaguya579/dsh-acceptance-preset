# ADR-0002 确定性层与 agent 语义层分工

- 状态：已接受（2026-08-16）
- 相关：ADR-0001（原生内建）、ADR-0003（路径语义）

## 背景

历史阶段（外部 Python 工具）采用「静态分析 + LLM 混合」：工具内串行调用三次 LLM（技术栈概述、偏差分析、画像/接手方案），任一调用超时即拖垮整轮——真实运行中出现「The read operation timed out → 无法判定」，用户体验为完全不可用。教训：**确定性底座与语义判断耦合在一条串行流水线里，语义层故障会摧毁整轮验收**。

## 决策

**确定性层与 agent 语义层彻底分离**：

1. 确定性层（插件内建）只产事实包（`确定性事实.json`，schema `acceptance-facts/1`），**绝不调用 LLM、绝不产出结论**；
2. 语义层全部由 DSH agent 完成：四类偏差识别、问题分级、业务画像、接手方案、验收结论——基于事实包 + 用 read/grep 下钻交付物代码与文档逐条取证；
3. 判定口径沿用历史工具：通过/打回/无法判定（无基线为建议通过/建议整改/无法判定）；「未检查」绝不表述为「无」；
4. 领域专项以业务描述知识文件随插件工程分发（`profiles/<专项>/业务描述.md`），agent 在相关验收前先读并按其检查重点逐项执行——继承历史「业务描述注入」思想，改为 agent 直接读取。

## 后果

- 确定性层无 LLM 依赖：永不超时、永不下错误结论、可离线复现；
- 语义判断质量随 harness 模型演进，无需升级插件；
- 验收报告/结论由 agent 临场产出，格式弹性大——代价是复验修复状态评估目前无结构化规则（见 backlog 04）；
- harness 本身即模型运行时，「LLM 不可用」意味着 agent 本身不可用，不再有工具内降级路径。

## 替代方案（已弃）

- **工具内 LLM 串行分析**（历史方案，已弃）：见背景；
- **工具内 LLM + agent 复核双层**：语义判断重复执行、责任不清，弃。
